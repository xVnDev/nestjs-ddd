# P05 · Step 1 — Local Auth & RS256 JWT

**Project:** nestjs-ddd  |  **Phase:** P05 — Authentication  |  **Base branch:** `dev`  |  **Status:** ⬜ Planned

> Source of truth: [`roadmap.md`](../../../roadmap.md) §4. Umbrella IDs `P05-01`, `P05-02`, `P05-03`, `P05-04` stay in the roadmap; this file lists the final atomic split (`P05-01a` … `P05-04d`).
> **Format**: `P<phase>-<umbrella><letter>` — one atomic task = one commit; sibling atomic tasks share one branch (branch per umbrella task). Every atomic task uses the 7-field format: `Description`, `CLI(s)`, `Package(s)`, `File(s)/Folder(s)`, `Branch`, `Commit`, `Testing`.
> **Ordering notes**: (a) `P02-02` already declares the `TOKEN_ISSUER` token; `P05-04a` only refines its domain types, then `P05-04b`/`P05-04c` add the RS256 JWT adapter and an in-memory fallback with one shared conformance spec (`P02-03` harness). (b) `P05-01a` builds the auth skeleton, `P05-01b` the thin Passport local strategy and `P05-01c` its specs; all credential checks go through `PASSWORD_HASHER` and `USER_REPOSITORY` tokens, never concrete adapters. (c) `P05-02a`'s login use case initially returns the authenticated principal + session only; `P05-04d` injects `TOKEN_ISSUER` into that same use case so the HTTP contract stabilises at "access + refresh tokens" without a controller change. (d) Key material is generated by `P05-03a` into gitignored paths — only env paths and a `kid` are committed; no private key ever enters source control.

## DDD + SOLID lens for this step

- Bounded contexts own `domain/`, `application/`, `infrastructure/`, `interfaces/`; dependencies point inward.
- Domain/application depend only on port tokens; adapters are injected, never imported directly.
- Every port ships one conformance spec run against all adapters, including in-memory fallbacks.
- Business rules live in entities/value objects/use cases; controllers stay thin.
- Introduce a port only when a mechanism must be swappable or isolated for tests.
- Passport strategies and guards are thin adapters: they translate HTTP/Credentials into a use case and never verify passwords or mint tokens themselves.
- Signing is RS256 with a `kid` in the JWT header; keys are loaded from validated env paths, never committed.

## Step Summary

Verify local credentials with a thin Passport strategy over the existing `PASSWORD_HASHER` port, expose a login endpoint backed by a single-purpose use case, configure RS256 keys with a `kid` from gitignored files, then add a conforming token issuer (JWT adapter + in-memory fallback), a thin JWT strategy/guard, and wire token issuance into the login response.
